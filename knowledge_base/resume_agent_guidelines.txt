文档名称：AI Agent 工程岗位简历优化规范
文档版本：1.0
文档用途：作为简历优化 Agent 的外部知识库测试文档
适用对象：申请 AI Agent Engineer、LLM Application Engineer、Python Backend Engineer 的候选人

============================================================
第一部分：使用说明
============================================================

本知识库用于辅助简历优化 Agent 进行岗位匹配、内容排序、项目表达和输出校验。
知识库中的内容属于简历写作与岗位匹配建议，不属于候选人的个人经历证明。
Agent 不得把本文件中的技术名词、工作成果或示例数字直接写入候选人简历，除非原始简历中存在对应事实证据。

当用户询问以下问题时，应优先检索本知识库：

1. 如何优化 AI Agent Engineer 简历。
2. 如何描述 LangGraph、RAG、Tool Calling、Human-in-the-loop 项目。
3. 如何设计岗位匹配分数。
4. 如何处理 JD 中有但原始简历没有的技能。
5. 如何避免简历事实夸大。
6. 如何提高 ATS 对技术关键词的识别效果。
7. 如何检查优化后的简历是否仍然忠于原始简历。

推荐引用格式：

[AI Agent 工程岗位简历优化规范，第 N 部分]

============================================================
第二部分：AI Agent Engineer 简历的核心能力模型
============================================================

AI Agent Engineer 的简历不应只罗列“大语言模型、RAG、Agent”等名词，而应体现完整的应用链路。推荐从以下六个维度分析候选人与岗位的匹配程度。

维度 A：模型应用能力

关注候选人是否有以下事实证据：

- 调用 Chat Model 或其他大语言模型接口。
- 设计 Prompt、System Prompt 或结构化输出格式。
- 使用 Function Calling、Tool Calling 或类似机制。
- 处理模型输出解析失败、超时或重试。
- 对模型回答质量进行评估或校验。

只有“使用过 ChatGPT”通常不足以证明模型应用开发能力。简历应该说明模型在什么业务流程中被使用，以及候选人负责了哪些工程工作。

维度 B：Agent 工作流能力

关注候选人是否有以下事实证据：

- 多步骤 Agent 流程。
- 状态管理和节点之间的数据传递。
- 条件路由或循环执行。
- 工具调用后的结果回传。
- 人工审批或 Human-in-the-loop。
- 任务失败后的重试、修复或降级。

如果候选人只写“开发了一个 Agent”，但没有说明流程、状态、工具和异常处理，可信度较低。

维度 C：RAG 与知识库能力

关注候选人是否有以下事实证据：

- PDF、Markdown、TXT 或网页文档加载。
- 文本切分、chunk overlap 或元数据保留。
- Embedding 和向量检索。
- Top-K、相似度阈值或检索结果过滤。
- 将检索结果注入 Prompt。
- 返回来源文件名、章节或页码。
- 处理知识库更新和重复索引。

只写“熟悉 RAG”不如写清楚“文档如何进入知识库、如何检索、如何被模型使用”。

维度 D：后端工程能力

关注候选人是否有以下事实证据：

- Python 服务开发。
- FastAPI 或其他 Web API 框架。
- Pydantic 数据校验。
- PostgreSQL 或其他数据库。
- Redis、缓存、异步任务或连接池。
- 日志、错误处理和测试。

AI Agent 项目仍然需要后端工程能力。只有 Prompt，没有 API、状态和数据存储，通常不能证明具备应用落地能力。

维度 E：可靠性与安全能力

关注候选人是否有以下事实证据：

- 结构化输出校验。
- 工具权限控制。
- 高风险操作人工审批。
- 超时与重试。
- 事实一致性检查。
- 敏感信息保护。
- 失败时返回可解释错误，而不是静默生成错误结果。

维度 F：产品交付能力

关注候选人是否有以下事实证据：

- 前端或 API 交互界面。
- 用户可以查看中间结果。
- 支持任务恢复或历史记录。
- 支持文件上传或导出。
- 能够展示引用、评分、修改说明和校验结果。

第三部分：岗位匹配分数建议
============================================================

岗位匹配分数的推荐范围是 0 到 1，展示给用户时可以转换成 0 到 100 分或百分比。

推荐的解释性权重如下：

- 核心技术能力匹配：35%
- Agent 或 LLM 应用经验匹配：25%
- 岗位职责匹配：20%
- 项目和工作结果相关性：10%
- 关键词覆盖：10%

这些权重是展示和解释用的建议，不是必须写死的数学公式。匹配 Agent 应优先关注核心能力和职责，不能只按照关键词出现次数计算分数。

分数解释建议：

90% 到 100%：核心技能、岗位职责和项目经历高度匹配，只有少量表达可以优化。

75% 到 89%：整体匹配较好，但仍有一到两个重要能力缺少明确证据或表达不够突出。

60% 到 74%：存在一定相关经验，但核心岗位要求有明显证据缺口。

低于 60%：当前简历与目标岗位差距较大，不建议通过改写文字掩盖能力缺口。

分数解释必须同时列出：

- matched：原始简历中有明确证据支持的要求。
- missing：当前简历中没有足够证据支持的要求。
- evidence_gap：可能有相关经历，但原始简历表达不够明确的要求。

“missing”不等于候选人一定没有该能力，只表示当前简历没有足够证据证明该能力。

============================================================
第四部分：事实边界与禁止夸大规则
============================================================

简历优化 Agent 必须把原始简历视为候选人事实的主要边界。

允许的修改：

- 调整项目和工作经历的顺序。
- 合并重复表达。
- 将口语化表达改为专业表达。
- 突出与目标岗位相关的已有技能。
- 使用更清晰的动词描述候选人已经做过的工作。
- 将原始经历重组为更容易被 ATS 识别的句子。
- 在不改变事实含义的前提下改善语法和结构。

禁止的修改：

- 添加原始简历没有出现的技术栈。
- 把“参与”改成“负责”或“主导”，除非原始内容支持。
- 把“使用过”改成“精通”。
- 添加原始简历不存在的公司、职位或项目。
- 添加原始简历不存在的性能提升数字。
- 添加原始简历不存在的用户规模、请求量或成本节省。
- 把学习经历改写成生产项目经验。
- 把相关技术经验推断成等价技术经验。

例如：

原始内容：参与 Agent 项目开发。

允许改写：参与基于大语言模型的 Agent 项目开发，协助完成相关功能实现。

不允许改写：主导企业级 Agent 平台架构设计，支撑百万级用户请求。

原始内容：优化了系统性能。

允许改写：参与系统性能优化，重点关注接口响应和数据访问流程。

不允许改写：将系统响应速度提升 40%。

如果优化建议需要候选人补充信息，应输出待确认问题，而不是直接生成内容。例如：

“你是否有该接口的平均响应时间或吞吐量数据？如果没有，建议不要添加具体百分比。”

第五部分：AI Agent 项目表达模板
============================================================

推荐使用以下结构描述 Agent 项目：

项目背景：项目解决什么问题，服务什么用户或业务流程。

Agent 目标：模型或 Agent 在流程中承担什么任务。

工作流：Agent 分为哪些步骤，是否包含条件路由、循环或审批。

工具和数据：调用了哪些工具，读取了哪些数据，是否使用 RAG 或外部 API。

工程实现：使用了哪些框架、数据库、接口和状态管理方案。

可靠性：如何处理结构化输出失败、工具失败、事实错误和高风险操作。

结果：只有在原始简历有明确证据时，才写性能、准确率、成本或效率结果。

示例模板：

“使用 [框架/技术] 构建 [业务场景] 的多步骤 Agent 工作流，完成 [具体任务]；通过 [工具/RAG/数据库] 获取 [数据类型]，并使用 [状态管理/结构化输出/校验机制] 保证 [可靠性目标]。”

如果原始简历中只有部分信息，应只填充有事实依据的部分，其余内容省略或标记为待补充。

============================================================
第六部分：RAG 项目表达规范
============================================================

一个可信的 RAG 项目描述通常包含四个阶段：

1. Ingestion：加载 PDF、Markdown、TXT 或其他文档。
2. Chunking：按照章节、页面或固定窗口切分文本，并保留来源元数据。
3. Retrieval：将查询转换为向量，检索 Top-K 相关 chunk，并根据相似度阈值过滤。
4. Generation：把检索结果作为上下文交给模型生成回答，并返回来源。

如果系统保留 PDF 页码，简历或项目说明可以明确写：

“对 PDF 文档进行按页解析和切分，保留页码元数据，并在回答中返回来源页码。”

如果系统只实现了向量检索，没有实现重排序、混合检索或引用校验，不应声称实现了这些能力。

以下表述需要谨慎：

- “支持 RAG”是宽泛描述，最好补充索引和检索流程。
- “解决了幻觉问题”过于绝对，建议改为“通过来源约束和事实校验降低无依据生成”。
- “保证回答 100% 正确”不应出现在简历中。
- “实现企业级知识库”需要有规模、权限、更新和监控证据，否则应改为“实现知识库问答原型”。

============================================================
第七部分：ATS 关键词与表达建议
============================================================

ATS 关键词优化的目标不是机械堆叠关键词，而是让已有经验使用岗位描述中的标准术语清晰表达。

推荐做法：

- 技术名词首次出现时使用完整名称。
- 在同一段经历中，将技术名词和实际工作动作放在一起。
- 使用岗位描述中的标准拼写，例如 LangGraph、PostgreSQL、FastAPI、Embedding、Vector Search。
- 将技术名词放在技能、项目和工作经历中合理出现。
- 同义词可以适度补充，例如“大语言模型（LLM）”，但不要重复堆叠。

不推荐做法：

- 在技能栏堆放没有项目证据的技术名词。
- 为了提高关键词覆盖率，直接把 JD 中的 Kubernetes、Kafka 或 AWS 写进简历。
- 重复同一个关键词十几次。
- 使用与实际经历不匹配的高级术语。

关键词覆盖率只能作为辅助指标，不能替代语义匹配和事实判断。

============================================================
第八部分：简历改写前后的校验规则
============================================================

改写后的简历至少应进行以下检查：

检查一：事实一致性

- 公司、职位、时间和项目名称没有新增或改变。
- 技术栈没有超出原始简历事实边界。
- 职责强度没有被无依据提升。
- 数字和结果没有被模型凭空添加。

检查二：岗位关键词覆盖

- 目标岗位的核心关键词是否在已有事实支持的范围内被清晰表达。
- 缺少证据的关键词不能强行补写。
- 对缺少证据的要求给出“建议后续补充真实经历”的提示。

检查三：表达质量

- 每条经历尽量包含动作、对象和结果。
- 避免连续使用“负责、参与、协助”等低信息密度动词。
- 避免空泛表达，例如“提升了能力”“取得了良好效果”。
- 项目描述应优先突出与目标岗位直接相关的内容。

检查四：格式质量

- 标题层级清晰。
- 时间格式统一。
- 没有连续多余空行。
- 没有明显的 Markdown、JSON 或模板残留。
- 简历长度和目标岗位要求相匹配。

校验失败时，Agent 应优先进入定向修复，而不是完全重新生成一份风格不同的简历。

============================================================
第九部分：引用和回答规则
============================================================

如果回答使用了本知识库中的具体规则，必须返回对应的来源名称和部分名称。

推荐回答格式：

“根据《AI Agent 工程岗位简历优化规范》第四部分，不能把‘参与 Agent 项目’改写成‘主导企业级 Agent 平台架构设计’，因为后者超出了原始事实边界。”

如果知识库中没有足够依据，Agent 应明确说明：

“当前知识库没有覆盖这一问题，以下内容是通用建议，不作为本知识库引用。”

长期用户记忆不能作为本知识库引用来源。用户之前说过的偏好只能影响输出风格，不能证明候选人的工作经历或技术能力。

预期命中：第二部分、第三部分。

预期命中：第四部分。

预期命中：第六部分。

“JD 里要求 Kubernetes，但我的简历没有 Kubernetes，可以直接补进去吗？”

预期命中：第四部分、第七部分。

“岗位匹配 82% 应该如何解释？”

预期命中：第三部分。

“如何校验优化后的简历没有被模型夸大？”

预期命中：第四部分、第八部分。

“Memory 中的用户偏好能不能作为简历经历的引用来源？”

预期命中：第九部分。
